Nityam Blueprints

Three Sanskrit names carry the whole system: Nityam — the constant, the tutor that's always there — is built on Smriti, remembered knowledge of the student, and Shruti, "that which is heard" — the teacher's own lecture, preserved rather than paraphrased. These five diagrams are the mechanism behind that: five agents, three memory tiers, one ingest pipeline, one deploy path.

Every box below carries a build note: shape, fill, and where a real Google Cloud icon replaces a dashed placeholder. ⚠ marks a place where the diagram shows a known gap rather than a finished path — read those before pasting them into a pitch deck.

Diagram 2 of 5

How VoiceAgent routes

VoiceAgent never blocks. Calling a specialist hands the tool off to ADK's background-task registry and immediately returns a synthetic, free "pending" response — the mechanism that keeps her talking while a specialist works underneath her. Three timers gate whether a chunk is allowed to interrupt; one lock keeps the same specialist from being called twice at once.

Diagram 3 of 5

Shruti — from lecture to citation

Ten stages turn a recording into a queryable knowledge substrate, each one independently re-runnable against its own cached input. ⚠ The last hop is honest, not finished: Shruti's own store (Cloud SQL + pgvector) is not the same place the tutor reads from at runtime (Firestore) — today a person runs seed_demo_data.py to bridge the two by hand.

Diagram 4 of 5

SMRITI — read every turn, write once, cite everything

Three tiers, ordered by how far back they reach. Reads happen continuously, from four call sites. Writes to the two permanent long-term documents happen exactly once — at session close — through a validated-operation gate, never a raw model overwrite. Every claim those documents hold cites a session_id#turn that has to resolve into a real Episodic entry.

Diagram 5 of 5

Inside one specialist call

Zooming into a single ask_board() call: VoiceAgent's own lifeline stays free the whole time. The specialist gets its own ADK Runner and session, seeded with {session_id, student_id}, and runs to a hard 70-second cap. Any exception — the same blanket handler for all four specialists — becomes a spoken error chunk, never a silent failure.

Honest status — what to actually claim

This project's own documentation has a rule worth keeping here: corrections get appended in place, not silently smoothed over. Before these diagrams go on a slide, know which parts are live, which are a disclosed workaround, and which are still an open question.

Live

Cloud Run, Cloud Build CI/CD, Artifact Registry, Secret Manager, Firestore ("smriti" db), Cloud Storage for artifacts, Firebase Auth, and Memorystore for Redis are all deployed and wired into the running service.

Manual, disclosed

Shruti's pipeline runs end to end and produces real, citable grounding chunks — but nothing yet automates the hop from its vault output into Firestore. seed_demo_data.py does that by hand today.

Open

Citation faithfulness (does the tutor's claim match what it retrieved) scored 5/5 in eval. Personalization and memory-causality — does the tutor visibly use what it remembers — is the system's own sharpest, still-unresolved finding.

Demo convenience

New sign-ins are auto-seeded with a fabricated memory history (NITYAM_SEED_NEW_STUDENTS) so a first session already looks personalized. Disclosed in-repo as a demo aid, not a real feature — turn it off for real students.
